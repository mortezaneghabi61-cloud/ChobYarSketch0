# V6.1 evidence timestamp precision and epoch rotation

## Proven production defect

Between 2026-09-11 19:21 UTC and 2026-09-12 04:48 UTC, the VPS shadow timer
completed 31 evidence captures and rejected 78 with:

`council_evidence.EvidenceError: capture timestamp does not match evaluation time`

`evaluation_time_unix` retains the platform float returned by `time.time()`.
`datetime.isoformat()` represents that instant at microsecond precision. Parsing
the ISO value back to a float and requiring exact numeric equality therefore
rejected valid submicrosecond values nondeterministically. This was a local
serialization comparison defect, not a network outage or a timer failure.

## Minimal correction

The record builder already writes `captured_at_utc` using the canonical UTC ISO
representation of `evaluation_time_unix`. Validation now recomputes that same
canonical representation and requires exact string equality. It does not widen a
time tolerance, alter the authoritative numeric evaluation time, or change replay
inputs, decisions, risk, trading mode, execution authority, or journal limits.

A regression uses a concrete submicrosecond timestamp that failed against the old
validator. It also proves that a one-microsecond semantic timestamp change remains
rejected even when the unkeyed record digest is recomputed.

## Engine epoch boundary

`council_evidence.py` is one of the six evidence engine files. Changing it must not
make old records appear to have been generated by the new source. The deployment
therefore performs a formal epoch rotation:

1. Validate the complete active V5.9 journal with the exact old engine.
2. Stop only the shadow timer and wait for its oneshot to become idle.
3. Move the old journal into a private epoch directory and copy all six old engine
   files beside it, with a SHA-256 manifest.
4. Replay the archived journal using that archived engine set.
5. Install only the corrected `council_evidence.py`.
6. Run one observation-only shadow evaluation to create and replay a private new
   active journal, then restore the timer.

The migration never rewrites an old record or digest. A failure restores the old
engine and journal and re-enables the timer. Trader and Status are not restarted;
their PID, monotonic start time and invocation identity must remain unchanged.

The V6.0 readiness clock restarts at the new reviewed engine epoch. This is not
selection of a favorable performance window: the preceding journal remains intact
and independently replayable, and the boundary is caused by a documented engine
defect. Every future active-epoch gap still counts against the coverage policy.

## Authority and readiness

The system remains Paper-only with the existing position, stop, take-profit and
daily-loss limits. Full-fidelity backtest readiness, execution/live authority,
automatic promotion and automatic reweighting remain false. A successful migration
only repairs continuous evidence collection; it makes no profitability claim.
